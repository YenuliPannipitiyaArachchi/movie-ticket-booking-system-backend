# Movie Ticket Booking System: Backend

Spring Boot REST API for an online movie ticket booking platform. Customers browse movies, theatres and shows, pick seats, book tickets and pay. Administrators manage users, movies, theatres, shows, bookings and payments. Security uses Spring Security with JWT.

Built for IJSE CMJD 114/115, Assignment 1.

## Technologies
Java 17, Spring Boot 3.3, Spring Web, Spring Data JPA (Hibernate), Spring Security + JWT (jjwt 0.12), MySQL 8, Bean Validation, Lombok, Maven, GitHub.

Architecture: **Controller -> Service -> Repository -> Database**, DTOs (Java records in `dto/Dtos.java`), enums for all roles and statuses, global exception handling (`GlobalExceptionHandler`), SLF4J logging in every service.

## Database configuration
1. Install MySQL 8 and start it.
2. Edit `src/main/resources/application.properties`, or set environment variables:
   - `DB_USERNAME` (default `root`)
   - `DB_PASSWORD` (default: empty, which works with a fresh Homebrew MySQL)
   - `JWT_SECRET` (Base64 string of at least 32 bytes; a development default is provided)
3. The database `movie_booking_db` is created automatically and tables are generated by Hibernate (`ddl-auto=update`).
4. On first start demo data is inserted (`app.seed=true`):

| Role | Email | Password |
|---|---|---|
| ADMIN | admin@movie.com | Admin123 |
| CUSTOMER | customer@movie.com | Customer123 |

Plus 4 movies, 2 theatres and 9 scheduled shows. Set `app.seed=false` to disable.

mvn clean package && java -jar target/movie-ticket-booking-1.0.0.jar

Seat numbers are stored in the `booking_seats` collection table (`booking_id`, `seat_number`). Seat ids look like `A1`..`J10` (letter = row, number 1-10, within the theatre capacity).

Enums: Role (ADMIN, CUSTOMER), MovieStatus (UPCOMING, NOW_SHOWING, ENDED), TheatreStatus (ACTIVE, INACTIVE), ShowStatus (SCHEDULED, COMPLETED, CANCELLED), BookingStatus (PENDING, CONFIRMED, CANCELLED), PaymentStatus (PENDING, COMPLETED, FAILED, REFUNDED), PaymentMethod (CARD, CASH, ONLINE).

## Authentication
1. `POST /api/auth/signup` registers a CUSTOMER (admins are created by seed data or by an admin updating a user's role).
2. `POST /api/auth/signin` returns `{ token, role, name, email }`.
3. Send the token on every protected request: `Authorization: Bearer <token>`.

Tokens expire after 24 hours (`app.jwt.expiration-ms`). Missing/invalid token -> `401`; wrong role -> `403`.

## Business rules implemented
- Only ADMIN creates/updates/deletes movies, theatres and shows; customers can view them.
- Shows need an existing movie and an ACTIVE theatre; ENDED movies cannot get shows; the same theatre cannot have two shows at the same date and time (409).
- Cancelled or completed shows (and shows already started) cannot be booked.
- A booking needs at least one seat; `numberOfTickets` must equal the number of seats; an already-booked seat for the same show returns 409. The show row is locked while booking to prevent double booking.
- `totalAmount = ticketPrice x numberOfTickets`.
- Cancelled bookings cannot be paid for. A COMPLETED payment confirms the booking; FAILED does not; a COMPLETED payment cannot be processed again. Cancelling a paid booking marks the payment REFUNDED.

## Sample API requests
```bash
# Sign in
curl -X POST http://localhost:8080/api/auth/signin -H "Content-Type: application/json" \
  -d '{"email":"customer@movie.com","password":"Customer123"}'

# Browse
curl "http://localhost:8080/api/movies?status=NOW_SHOWING"
curl "http://localhost:8080/api/shows?movieId=1&date=2026-10-12"
curl http://localhost:8080/api/shows/1

# Book seats (token from sign-in)
curl -X POST http://localhost:8080/api/bookings -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"showId":1,"seatNumbers":["A1","A2","A3"],"numberOfTickets":3}'

# Pay: create, then process
curl -X POST http://localhost:8080/api/payments -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"bookingId":1,"method":"CARD"}'
curl -X POST http://localhost:8080/api/payments/1/process -H "Authorization: Bearer $TOKEN"

# Cancel
curl -X PUT http://localhost:8080/api/bookings/1/cancel -H "Authorization: Bearer $TOKEN"

# Admin: create a movie
curl -X POST http://localhost:8080/api/movies -H "Authorization: Bearer $ADMIN_TOKEN" -H "Content-Type: application/json" \
  -d '{"title":"New Film","genre":"Action","language":"English","durationMinutes":110,"status":"NOW_SHOWING"}'
```
Errors share one shape: `{ "timestamp", "status", "error", "message", "fieldErrors"? }`.

## Future expansion proposals
**1. Multiple screens and seat categories**
- *Feature:* A theatre has several screens, each with its own seat layout and seat types (standard, premium) at different prices.
- *Why useful:* Realistic capacity, tiered pricing, and a true seat map instead of a single capacity number.
- *Existing entities affected:* Theatre (capacity moves to screens), Show (links to a screen), Booking (seats reference real seat records).
- *New entities:* `Screen`, `Seat` (and optionally `SeatCategory`).
- *Relationships:* Theatre 1:M Screen, Screen 1:M Seat, Show M:1 Screen, Booking M:M Seat (join table `booking_seats` with seat_id).

**2. Discount and promotional codes**
- *Feature:* Customers enter a promo code to reduce the booking total.
- *Why useful:* Drives repeat bookings and lets admins run offers.
- *Existing entities affected:* Booking (stores discount and final amount), Payment (charged amount).
- *New entities:* `PromoCode` (code, percentage/amount, validity dates, usage limit).
- *Relationships:* PromoCode 1:M Booking (nullable FK `promo_code_id`); optional `PromoUsage` for per-user limits (User M:M PromoCode).
